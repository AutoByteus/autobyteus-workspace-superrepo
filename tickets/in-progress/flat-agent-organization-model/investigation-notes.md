## Product And Domain Understanding

- Product area: AgentTeam definition, execution topology, collaboration handoffs, logical addressing, persistence/history, memory layout, task delegation, and AgentTeam frontend surfaces.
- Affected actors or systems: Agent package authors, end users launching and inspecting collaborative runs, Team-bound Agents using collaboration tools, backend definition/run services, and the web client.
- Existing user or operational purpose: Define reusable coordinator-led Teams, mount Teams recursively, launch one rooted collaboration tree, address mounted Agents/Teams with canonical `/...` addresses, and compile definition-local handoffs into the run snapshot.
- Relevant terminology:
  - **AgentTeam (current):** A coordinator-led definition whose direct members may be Agents or AgentTeams.
  - **Nested AgentTeam (current):** A Team definition mounted as a member of another Team definition.
  - **Agent Organization (proposed):** A top-level collaboration container that would contain flat Teams and independent Agents.
  - **Flat Team (proposed):** A coordinator-led Team whose direct members are Agents only.
  - **Organization handoff (proposed):** An edge between mounted Agent or Team placements inside one Organization.

## Requirement Implications

1. The user's instinct is supported by observed usage: all inspected organization-like packages and stored runs use exactly Organization → Team → Agent depth, not arbitrary recursive Teams.
2. The current root Team already provides the shared address and handoff graph the proposed Organization needs. A fixed-depth Organization can preserve `/agent`, `/team`, and `/team/agent` placement semantics.
3. Current handoff rules do not connect independent root runs by logical address. Therefore one Organization run/collaboration scope is the simpler target; independent Team runs connected dynamically would be a different, larger capability.
4. Flat Teams remain coordinator-led, while AgentOrg is coordinator-free. Org activation does not choose a recipient; an exact Agent or Team focus is required only when the user initiates a recipient-requiring interaction after launch.
5. The current Team V2 topology supplies the reusable child/handoff/task records, but it remains the native standalone Team file. AgentOrg needs a separate V1 root/file because `rootTeam` requires coordinator semantics; reuse does not justify a persisted generic V3 union.
6. The established migration input has no deeply nested configured topology, so Architecture Design does not need a deep legacy conversion or compatibility branch.
7. Removing recursive nesting is a structural contract/persistence change, not a local cleanup. Architecture Design will be required after requirements approval.
8. Because definition, launch, and history surfaces currently encode root-Team and recursive-Team assumptions, the requested prototype is a material coordination artifact for the UI/API cutover even though it does not change the already-approved domain contract by itself.
9. The current handoff record already supplies a stable user mental model: a Handoff is one From/To route and its `rules[]` are ordered natural-language When conditions. Product Design does not need a new policy language, but it does need complete authoring, validation, ordering, and scope ownership behavior.
10. Org-owned endpoint choices must project the fixed-depth configured topology, including Agents mounted inside referenced Teams; Team-local choices stay direct-Agent-only. This preserves Team reuse while letting Org workflow reach exact mounted placements.
11. Current AgentTeam behavior already supplies the desired configuration-first analogue: Team `Run` prepares configuration, and the root/Team/Agent hierarchy resolves defaults and placement overrides. The Org adaptation removes coordinator-derived initial focus, reduces precedence to fixed depth, and launches the complete scope.
12. Configuration inheritance and recipient focus are orthogonal. Org-root/Team/Agent settings determine how mounted executions run; the post-launch sidebar focus determines which exact Agent receives user communication, with Team focus resolving through the Team coordinator.
13. Approved `RV-012` supplies the normative product presentation for the structural requirements: it confirms the fixed-depth model without changing the underlying contract, and every visible final-reference detail is binding unless Product explicitly marks fixture content as illustrative.
14. The prototype's local deterministic behavior validates the reviewed product interaction, not production services. Architecture must map that experience to real persistence, validation, orchestration, streams, concurrency, permissions, and lifecycle contracts.
15. Mixed history/stream/workspace readers need an explicit `agent_team`/`agent_org` discriminator because two strict file families coexist. Flat Team V2 is already target state; only one-level organization-like roots require a family conversion.
16. The original 23 definition roots remain valid topology/scenario evidence but no longer establish a writable migration cohort. Source ownership, not physical accessibility, decides whether this ticket may transform a definition.
17. Stored run packages are server-owned durable snapshots. Their migration/history obligation does not disappear when the originating definition repository is external or temporarily incompatible with the target codec.
18. One target-only normal codec is simpler than retaining both recursive and flat Team definition parsers. The approved cost is explicit, diagnosable per-definition unavailability until separate owners publish exact target versions.
19. The original Team hierarchy's aggregate status dot is reusable as a presentation contract, not a lifecycle model. The existing five-state fold already proves that exact Agent statuses can summarize a Team branch while remaining collapsed-visible, accessible, non-persisted, and non-authoritative.
20. The user explicitly confirms that the mounted-Team UI aggregate is behaviorally the same as the prior nested-AgentTeam UI aggregate. This supports preserving the five-state projection but does not require Requirements Engineering to select a component, state store, or code-reuse path.
21. The existing AgentTeam launch hierarchy already provides the desired progressive-disclosure and inheritance language. AgentOrg should preserve that observable behavior for mounted-Team overrides, but parity does not imply identical runtime models, launch payloads, or component architecture.
22. The approved focused Product result resolves two presentation choices inside that behavior: the outer label exposes the exact configurable-Agent count with an adjacent disclosure, and Team coordinator identity stays on the exact coordinator Agent row. These are visible Product contracts, not new Org coordination or runtime ownership.
23. A sparse override representation is not itself a user contract. What matters is that preview, validation, launch request semantics, server resolution, and the durable snapshot identify the same effective runtime/model/configuration at every exact placement.
24. The Workspaces tree is durable navigation context, not an AgentOrg route decoration. Incorporating Org roots into the standard shell preserves one mental model and does not imply recursive configured Teams or an Org coordinator.
25. Workspace defaulting and communication focus are orthogonal. Selecting an actually available Temp Workspace prepares execution storage; it does not choose a message recipient. Root-to-Team inheritance remains compatible with exact Team placement overrides and explicit user choice.
